# Death Metal Cat -- Three-Agent Content Pipeline

**Purpose:** Death Metal Cat is a 2D side-scroller (GDD Section 4.2) whose city-biome rooms and
Cayde's kill/damage/environment voice lines are generated by a crew of three cooperating Claude
API agents rather than hand-authored one at a time. This doc + `docs/agent_crew_diagram.mmd` +
the integration test in `Tools/test_agent_crew_pipeline.py` demonstrate that the crew actually
works as a *pipeline* -- each agent's output is a real input another agent depends on -- not
just three scripts that each happen to work in isolation.

## The crew

| # | Agent | Input | Output |
|---|---|---|---|
| 1 | **Room Geometry Designer** (`Tools/room_geometry_designer.py`) | `room_id`, `difficulty_tier`, `room_role`, `target_room_length`, plus Cayde's real measured movement constants (jump height/distance, wall-jump/dodge reach) | `pieces[]` (ordered traversal sequence: flat runs, gaps, wall-jump shafts, ledges, drop-downs, enemy arenas) + `spawn_markers[]` (`marker_id`, `marker_type`: `EnemySpawn`/`PickupSpawn`, `after_piece_index`) |
| 2 | **Level & Encounter Designer** (`Tools/level_encounter_designer.py`) | A room's `difficulty_tier`/`room_role` + the *exact* `spawn_markers[]` list Room Geometry Designer placed | `populations[]` -- one decision per marker: `enemy` (with a count), `pickup`, or `empty`, each with a rationale tied to the GDD's difficulty curve |
| 3 | **Quip Generator** (`Tools/quip_generator.py`) | A trigger type (`kill`/`damage`/`environment`) + optional context tag, constrained by Cayde's locked voice profile | `{line, sound_tag}` -- a short in-character voice line and an invented placeholder sound cue |

### Role Clarity: why no agent is removable

Each agent's output is the next agent's *only* source of the information it needs -- this isn't
just a suggested order, it's a hard dependency in both directions:

- **Remove Room Geometry Designer** and Level & Encounter Designer has no `spawn_markers[]` to
  make a decision about at all -- there is nowhere else in the project that a room's marker list
  comes from.
- **Remove Level & Encounter Designer** and nothing ever decides *which* of Room Geometry
  Designer's markers becomes an enemy -- Quip Generator would have no way to know a kill event
  is even possible at a given marker, since `AEncounterSpawnMarker` is data-only with no logic of
  its own to make that call.
- **Remove Quip Generator** and an enemy dying at a populated marker has no voice line at all --
  Level & Encounter Designer's decision would be correct but silent, since it never generates
  dialogue itself.

The integration test proves this dependency chain concretely, not just in theory: see "What this
demo actually proved" below -- Quip Generator was called exactly once, and only because Level &
Encounter Designer's decision for one specific marker said so.

## What this demo actually proved

Before building anything, I checked whether Level & Encounter Designer was still a stub, as the
last session's notes suggested. **It wasn't.** It's fully built and was already committed and
proven against all 9 real rooms in a prior commit (`553a007`, "Prove out the Level & Encounter
Designer agent against all 9 real rooms") -- I verified this both by reading the script (it's a
complete implementation with the same generate-then-deterministically-validate architecture as
Room Geometry Designer, not a schema stub) and by invoking it live against a scratch folder,
which produced valid output on the first try. No agent needed to be built or stubbed for this
test -- all three were already real, working implementations.

`Tools/test_agent_crew_pipeline.py` is a **sandboxed integration test**, run for real against
the live Claude API (not mocked), that proves the *handoff* between agents rather than each
one's isolated correctness (each was already individually proven before this test existed):

- **Step 1** ran Room Geometry Designer for `Room1` (role `linear`, tier `1`) as a fresh,
  isolated generation -- it did not read or overwrite Room1's real committed
  `Tools/room_geometry_Room1.json`.
- **Step 2** took that exact in-memory `spawn_markers` list -- no disk roundtrip, no
  modification -- and passed it straight into Level & Encounter Designer's own
  `generate_valid_population()`, the same function its real CLI calls.
- **Step 3** looked at Step 2's decisions and, for every marker populated with an `"enemy"`,
  called Quip Generator for a `"kill"`-trigger line in Cayde's voice -- i.e. the literal quip
  that would fire when that specific spawned enemy dies.
- **Step 4** combined all three agents' outputs into one trace, keyed by `marker_id`
  (`Tools/test_output/pipeline_run_room1.json`), so it's visible at a glance that agent 2's
  decision for a marker is exactly what determined whether agent 3 was called for it at all.

The actual run: Room Geometry Designer generated a 9-piece Room1 with 4 spawn markers. Level &
Encounter Designer populated them as 1 enemy / 2 pickup / 1 empty, with each rationale
explicitly reasoning about the tier-1 "forgiving early room" curve from GDD Section 7. Quip
Generator was then called exactly once -- only for the one marker (`sm_003`) that came back
`"enemy"` -- and returned `"Tch. Should've run."` (`growl_short_03`). The other three markers
show `quip_selected: null` in the trace, since only an enemy marker warrants a kill quip. That's
the handoff proof: agent 2's decision is what determined whether agent 3 was even called for
that marker, and agent 3's output is what would actually be voiced for that specific encounter.

## What's still not proven / not built

- **Placement is still a separate, unbuilt step.** All three agents produce population/geometry
  *decisions* only -- no agent spawns an actual enemy or pickup actor in the level.
  `AEncounterSpawnMarker` is explicitly data-only with no spawn logic of its own.
- **No pickup-type taxonomy exists yet.** `"Generic"` is the only pickup type in the project --
  an honest placeholder, not an invented item economy.
- **This test only ran Room1.** Level & Encounter Designer has separately been proven against
  all 9 real rooms before, but this specific *pipeline handoff* test only exercises one room's
  worth of data.
- **Balance/QA Reviewer** (mentioned in Level & Encounter Designer's own prompt as the agent
  that will later check density/pacing rationales) does not exist as part of this three-agent
  crew and isn't exercised here.

## Sandboxing

This was a sandboxed demo run for a class assignment, not a real build step. It called each
agent's generation function directly and wrote JSON only under `Tools/test_output/`. It never
called `Tools/import_room_geometry.py`, `Tools/spawn_encounter_actors.py`, or any other script
that opens a connection to the live UE5 editor -- no level content, room actor, or committed
JSON in this project was read from or modified by this test.

**Update (later, separate step):** as a follow-up beyond the class assignment, the actual
`import_room_geometry.py` + `spawn_encounter_actors.py` "golden room" scripts were run for real
against Room7 (the next unbuilt room in the real progression), using Room7's already-committed
JSON. This *did* create real, permanent actors in the live level. See
`Tools/test_output/golden_script_room7_live_build.json` and `docs/golden_room_script_README.md`
for what that step did and why Room7 (not any of the sandboxed test's outputs) was the safe
target.
